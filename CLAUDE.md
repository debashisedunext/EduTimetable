# CLAUDE.md — EduTimetable (AI-Powered School Timetable System)

## What this project is

An AI-powered school timetable generation system for the **Edunext School ERP platform**. It guarantees **100% conflict-free auto-generation** by splitting the problem into two hard phases:

- **Phase A — Feasibility Engine:** pure arithmetic/graph checks that run *before* any slot is placed, proving a complete solution can exist (or naming the exact master-data row to fix). Surfaced as a live "Readiness Score" that updates on every master-data edit.
- **Phase B — Constraint Solver:** a CSP solver (backtracking + MRV/LCV/degree heuristics + forward checking + conflict-directed backjumping, with a min-conflicts local-search fallback) that only runs once Phase A has proved feasibility — so it cannot fail.

This two-phase split is the load-bearing architectural decision. Everything else is built around it.

## Docker-only development (hard rule)

The application is developed, tested, and run **exclusively inside Docker** — never on the host:

- The Docker Compose stack (`docker-compose.yml` + `docker-compose.override.yml` dev overrides, auto-loaded) defines every service: `api` (NestJS), `web` (React/Vite), `worker` (solver, BullMQ consumer), `optimizer` (Python CP-SAT, §5.6 soft optimization), `mysql` (MySQL 8), `redis`. `docker compose up` is the only supported way to start the app (production: `docker compose -f docker-compose.yml up`). Host ports: api **3001**, web **5174** — 3000/5173 are occupied by an unrelated SSH tunnel on the primary dev machine; inside the network it's always `api:3000`.
- **Never install or run Node, MySQL, or Redis on the host, and never suggest doing so.** All commands — dependency install, migrations, seeds, tests, lint, one-off scripts — run inside containers: `docker compose exec api pnpm test`, `docker compose exec api pnpm migrate`, etc. If the stack isn't running, use `docker compose run --rm <service> <cmd>`.
- Dev and production share the same multi-stage Dockerfiles; dev overrides add bind mounts and hot reload. CI builds and tests the same images. A change that only works outside Docker is broken by definition.
- **`PrismaService` is a pointer, not a connection** (§17.5): a proxy that resolves the current request's database from the tenant context. Never construct a `PrismaClient` in feature code — inject `PrismaService`. A dedicated school's `school_id` is usually 1, the same as the shared school's, so **tenant id is the routing key**; anything that writes outside a request (worker, queue listeners) must resolve its own connection from the job's `tenantId`. Connections are bounded by `TENANT_MAX_CLIENTS × TENANT_POOL_LIMIT`; `GET /health` reports the budget. `pnpm tenant:create` provisions a dedicated school — creating a database is an operator command, never something a login triggers.
- **A migration is not deployed until every school's database has it** (§17.3). `pnpm --filter @edutimetable/api migrate:all` walks the tenant registry (add `--dry-run` to report only); the shared database is migrated once however many schools live in it. A database behind this build is **refused on connect** with a message naming the fix — never served, because serving it produces `Unknown column …` on a random screen instead.
- **Two Prisma schemas, two migration histories.** `prisma/schema.prisma` is the application (one database per shared tenant group); `prisma/control/schema.prisma` is the §17.3 tenant registry, in its own database on the same server with its own generated client (`prisma/generated/control-client`, git-ignored). App: `prisma migrate deploy` / `pnpm seed`. Control: `pnpm migrate:control` / `pnpm generate:control` / `pnpm seed:control`. They are separate because a dedicated tenant's connection details cannot live inside a tenant database, and because Prisma cannot host two histories in one schema.
- Connection config comes from compose environment variables (service names as hosts: `mysql`, `redis`) — never `localhost` hardcoded in app code.
- **Watcher caveat:** bind-mount file events don't reach the containers on macOS; Vite polls (reliable), but Nest's tsc watcher can still miss edits — after changing api code, if behavior looks stale, `docker compose restart api` (30s) is the fix. Never debug "my change has no effect" without first ruling this out.

## Tech stack (as specified — do not substitute without discussion)

- **Frontend:** React + TypeScript, `@dnd-kit` for drag-and-drop (not react-beautiful-dnd), Zustand/Redux for the in-memory timetable grid, TailwindCSS, virtualized grid (`react-window` / AG Grid) for the 50×40 allocation matrix.
- **Backend:** Node.js (NestJS recommended), MySQL 8 (or Postgres), Redis + BullMQ for the solver job queue, Socket.IO for solver progress streaming and live conflict alerts.
- **Solver:** pure Node/TypeScript custom CSP engine owns feasibility. Google OR-Tools CP-SAT (Phase 6, `optimizer` compose service — Python, since OR-Tools has no official Node bindings) adds *soft* optimization only: it receives the already-pruned domains, and its answer is replayed through the same `SolverState.check()` and adopted only if it verifies AND scores better (§5.6). Optimizer down = fast-mode fallback, never a failed generation.
- **Background jobs are scheduled fairly across schools** (§17.7): the worker runs `SOLVER_CONCURRENCY` (default 3) jobs at once with a **per-school cap of one**, so a long generation in one school cannot block every other school and no school can take every slot. A capped job is deferred (`moveToDelayed` + `DelayedError`), never failed. Never set the worker back to `concurrency: 1`, and never release a school's slot without checking you still hold it.
- **A period number is not a row identity** (§10.6). A card can span two wings (§3.10), so `GridRow.key` is uniformly `c{configId}p{periodNumber}` and the grid map is keyed `${day}:${key}` — never the bare period number, which silently collided Junior's Monday P3 with Senior's (3 of 20 lessons lost on a two-wing fixture) and left lessons at period numbers the chosen wing lacked with no row to be drawn in at all. `shapeFor(configIds)` returns the **union** of wings' rows ordered by clock; rows are deliberately **not merged** across wings, because a card is true of one entity and merging would have to pick one of two period numbers — aligning cards to one clock is a property of a *wall*, so it lives on the client. Never re-derive a grid key at a call site: `rowKey`/`cellKey` are exported so the writer and every reader cannot disagree (the report-cache smoke mirrors them and had to be updated in the same change). **Room and subject cards need `view.all`**, unlike everything else in the Reports module where scope is a row-level filter: a filtered room grid says "Lab 2 is free" when a class is in it, which is a wrong answer rather than a smaller one. The room card must include §4.9 option rows or an elective's room reads as free. `GET /reports/wall?cards=t:1,cs:44,…` serves many cards at once (§29.3's `units=` idiom), capped at 24 with the cap **reported**; a refused card comes back as `{denied, reason}` in its own place so one refusal cannot blank a shared wall, and only `Forbidden`/`NotFound` are caught — anything else must still 500. The wall's clock axis is only truthful because of §28.5 (one period duration per config). **The wall is a column of flex rows, never one CSS grid over every cell**: a grid item taller than its track is *not clipped by the track*, it is painted over the next row, so any disagreement between a card's height and its track's height becomes an overlap — and `overflow: hidden` on the card cannot save it, because what overflows is the track, not the card. Two goes at making the two heights agree (`minmax(0, auto)` → `auto`, then `alignContent: start`) both failed. A flex row is as tall as its tallest child by construction and the next row begins after it, so there is no second height to disagree with. Generally: when a layout's correctness depends on two independently-computed heights agreeing, pick the structure where only one height exists.
- **`classes.sequence` IS the `CLASS_LADDER` position** (§31.12) — one definition, `ladderSequence` in `packages/shared`, and `classSequence` in the API resolves it for the three doors that create a class (`POST /classes`, the §16 importer, the §23 ERP sync). All three used to default to **`0`**, which is not "at the end" but *first*, tied with every other class created that way; the guided setup meanwhile wrote the ladder position, so a school hand-numbered 1..14 with no LKG got a collision the moment one was added and every `orderBy: [{class: {sequence}}, {section: {name}}]` in the app drew the tie arbitrarily. It is **not only an ordering**: `bandOf` and `subjectSuitsClass` compare the number against *absolute* ladder positions, so a gap-closing renumber would leave Class 9 reading as "upper". An off-ladder name gets **0** from `ladderSequence` and is placed after the ladder by `classSequence` — never interleaved on a guess, which is how the two vocabularies started. The repair migration touches only schools whose every class name is on the ladder; a school with its own vocabulary is left alone.
- **A cohort row belongs to a resource POOL, not to a school-year** (§30, Phase 43). `class_sections` is unique on `(class, section, academic_year, resource_group_id)`, so invariant 11 now reads *"**within a resource group**, a class-section belongs to exactly one `timetable_config`"* — identical in meaning while every school has one pool, which is what the migration backfills. The pool **owns** the row; `timetable_config_id` means "which timetable in this pool teaches it" and NULL still means "not attached yet". **`ResourceGroupService` is the only writer** of both `resource_group_id` columns (`@Global`, like `FreezeService`, because the failure mode is a new write path that never asks): they are one fact stored twice and MySQL cannot tie them together — a generated column may only read its own row, so §22's `draft_scope` trick is unavailable here. Never set either column at a call site. `pnpm test:groups` runs the drift check across the **whole database**, since the path that forgot is by definition the one not under test. **`sync.service.ts` types its transaction client as `any`**, so a missing required column compiles there and fails at runtime — it is the one file where tsc is not the safety net. Smoke scripts writing with a raw client share `scripts/resource-groups.cjs`. **"An individual timetable cannot have more than one wing" is `assertAdmits`** — a property of the pool, never a rule a screen remembers. **The §16 importer decides a class-section already exists by label AND pool** (`classSectionsInPool`, a list kept separate from `classSections` because that one is every other sheet's reference pool and the template's list): by label alone an individual timetable importing Class 1-A finds the main wing's, skips it, and opens with no classes and no error. **A clash between two LIVE timetables is compared by wall clock, never by period number** (§30.7): Junior's P3 and Senior's P2 both start 09:14, so period numbers are wrong in both directions — `findClashes` in `packages/shared` is the arithmetic, and §28.5's tick-based occupancy is still the real answer for *preventing* one. It is **not a feasibility Check**: the engine is Phase A over a snapshot of demand with no placements, so `ValidityService.clashesFor` computes it and `ReadinessService` appends it after `runFeasibility` — and after the **score**, because a clash does not make this timetable less able to generate (§28.1's rule). Always a warning with no remedy. Occupancy must include §4.9 option rows (no class-section, so a section query misses them) and dedupe §4.10 merged groups to one event per cell. **`invalidateTimetable` sweeps readiness by pattern**, because a readiness answer is no longer about one timetable alone — publishing B changes what A says, and the stale key belongs to a different config from the one being published. **Moving a timetable between pools recomputes its plan at apply** (§30.6a) and writes both pool columns in ONE transaction — a half-applied move is the drift `test:groups` exists to catch. Grouped→individual is always safe and *loosens*; individual→grouped refuses **by name** when the destination already holds that class-section. An emptied *individual* pool is deleted only when it holds neither a timetable nor an unattached cohort row; a grouped pool is the session's and is never removed. The plan reports exact before/after teacher totals, never a predicted Readiness score. Not freeze-guarded, but audited and Readiness dropped at once, so the accepted risk stays answerable. Pickers pass `?timetableConfigId=` to narrow to the selected timetable's pool; the **Classes master deliberately does not filter**, because it manages unattached rows too and already has a Timetable column to tell duplicates apart. **`crossConfigTeacherLoad` in `solver/input.ts` is the only cross-timetable calculation in the codebase** — it filters by pool, not by academic year (a pool belongs to one session, so that subsumes the year filter rather than sitting beside it), and §29.3's reassignment engine reads the same field off the same snapshot, so never add a second one. **A timetable says WHEN it applies** (§30.5): `effective_from`/`effective_to`, both nullable, null meaning the whole session — and **two published timetables whose windows overlap may not share a class**. `ValidityService` owns it, checked at publish AND at re-dating (re-dating passes the *proposed* window so nothing is written before the question is answered). By **class**, never class-section — with pools those are different rows for the same children. Against **live** publications only, so §3.14 withdrawal frees the window. **Never retroactive**: a window ending unpublishes nothing, because publication is a decision and not a lease. `windowLabel` (in `packages/shared`, one definition for server prose and client chrome) returns **null** for an undated timetable and callers fall back to the session's name — never print a date range for a school that has not set one. Not built on §25 terms: a session is term-wise iff it has term rows, so dating a timetable that way would flip the whole app into term-wise mode. **`capacityForClass` stays year-wide on purpose**: the curriculum is shared across pools, so a row must fit *every* pool that teaches the class — scoping it to one pool turns a form error into a Readiness blocker in a different timetable.
- **A wing carries its §30 pool, and the guided setup narrows to one** (§30.9). `WingAnswer.individual` identifies the pool completely — an individual pool holds exactly one timetable (`assertAdmits`), so the wing IS the pool, and absent means the session's shared one. `wingScope()` in `packages/shared` is that identity and `planClasses` keys its class-claim map on `(pool, class)`: two grouped wings claiming Class 6 is still an error, a grouped wing and an individual timetable both running Class 1 is not, and telling a school otherwise offered it two fixes it must not make. **`individual` is stamped from the database on every read, never trusted from the draft** — it is a fact about the timetable, changeable by §30.6a, and every draft saved before the field existed carries none. The wizard narrows **once**, handing each step `answersInScope` and splicing edits back in `patch`, because `wings` is read by the ladder, the week, the room suggestion, the teacher pinning, `planClasses` and two summary boxes; the stored draft always keeps every wing. Any step holding an active-wing index must clamp it — a list that shrinks under a stored index renders "add a wing first" for a wing that is there. The scope switcher shows only when a school has more than one pool. **The Master Grid's Lesson Grid needs the same narrowing** (`AllocationTab`'s `individual` prop off `resourceMode`): `computeLoads` sums a teacher across every wing it is handed, so without it six periods in the main school and four in an individual timetable read as ten against one limit. **Independence is a property of the timetable, never of the request** (§30.11): two timetables are comparable **iff they share a `resource_group_id`** — one predicate, no mode check, because `assertAdmits` means an individual pool holds exactly one timetable. Every comparison site filters on that column: `planClasses`, `crossConfigTeacherLoad`, **`assertPublishable` (§30.5)** and **`clashesFor` (§30.7)**. The last two used to cross pools deliberately — §30.5's comment argued *for* it, and is rewritten, because blocking an individual timetable over a timetable it cannot see is the decision not being kept; across pools §30.5 is now **silent**, chosen knowing the cost (if the two really do run at the same time of day, nothing says so), while within a pool both rules are untouched. **`commit` refuses pool by pool FROM THE DATA** — pools with issues are dropped, the rest are BUILT, refusals ride back in the response; every `planClasses` issue carries its `scope` to make that possible, and narrowing the request would only have hidden it, since a caller that forgot `?scope=` got the old behaviour. **There is no cross-timetable occupancy constraint in the database**: `uq_class/teacher/room_slot` are all keyed by `timetable_config_id`. **The COMMIT is scoped too, and that is the half a school actually hits**: `commit(4)` runs `planClasses` over the wings it is handed and the server commits from the *stored* draft, so setting up an individual timetable was refused with a real clash between two grouped wings — named on a screen showing neither and unfixable from it. `/onboarding/commit/:step` and `/preview/:step` take `?scope=`, applied once by `narrowToScope` (steps 7 and 8 read wings too); an **unknown** scope is refused, never ignored, or the bug returns silently. Changing scope clears the error banner, which is state and otherwise reads as a fresh refusal. **The error banner is stamped with the pool that raised it** (§30.10) and rendered only there — `error` was a bare string written from nine places, so a real clash between two grouped wings stayed on screen after switching to an individual timetable; Fast Refresh preserves state, so it could even outlive the code that raised it. `next()` clears it first, not after the save. **Deliberately still shared: the curriculum** — `class_subjects` has no pool column and `capacityForClass` stays year-wide, so an individual timetable running Class 5 inherits Class 5's periods-per-week; giving it its own is a schema change, not a validation tweak. `pnpm test:pools` is the proof.
- **The Master Grid is five pivots of one payload at 27 pixels a column** (§31, `/master-grid`). 5 days x 11 periods is 55 columns; on a 1,920px screen that is **27 pixels each**, which holds three characters — so the cells carry initials and short codes, §10.5's colour carries the second fact, the tab rail is **vertical** (horizontal tabs cost a row of school; vertical ones cost 34px the row header wanted anyway), breaks are a hairline column with their name on the tooltip, and **no emoji marker goes in a cell** (a lock glyph is 40% of the width — a pin is a dark left border, and a substitution keeps its cyan). Column widths are **percentages** so "no horizontal scroll" is a property of the layout, with a `minWidth` below which it scrolls rather than shrinking a cell below what a character fits in. Four of the five tabs differ only by **which field of the tuple names the row**, so `pivotSlots`/`PIVOT_FIELD` in `packages/shared` is one function and one table — four copies is how three handle §4.9 right and the fourth does not (§10.6's `rowKey`/`cellKey` lesson). Which rows fall out of which pivot **is invariant 9**: a section pivot skips option rows, a teacher pivot skips member rows and **keeps** the options, a room pivot skips nothing (a room used only by an elective option is occupied, and reporting it free is a wrong answer rather than a smaller one). **"How many things are in this cell" has two right answers** and `cellEvents` owns it: on the teacher pivot a §4.10 merged group is ONE occupancy event, on the subject pivot the same rows are N sections doing the subject (§10.6's density count) — on the reference school *every* teacher cell holding more than one row is a merged group, so this is what the tab shows rather than an edge case. **The Lesson grid is the odd tab out**: class-sections down, SUBJECTS across, periods per week from the **curriculum** (`GET /:id/context`, deliberately not `masters.manage`'s `/class-subjects`, or a principal meets a 403 on one tab of five), cells keyed by **class** because periods are a class fact (§27), year-filtered (§3.11), and `weekCapacity` from the wing's own week — never `capacityForClass`, which is year-wide because it guards a *write*. **Read-only, deliberately**: §27 owns curriculum and mappings, the Board owns placement, and it does not replace the Matrix (wide cells for reading one class's week against narrow ones for the shape of the school's). **`initialsOf` is one definition** (`packages/shared`) returning the school's stored `teachers.initials` untouched and deriving three characters only when they have never given any — there were two disagreeing derivations before, so the same person was `RKS` on one screen and `RK` on the next. Blank stores NULL, never `""`: empty means "not stated" (invariant 7) and a stored "nothing" paints a blank 27px cell that reads as a free period. **The strip is the other half of the design, not an addition to it** (§31.6): a grid with 27-pixel cells needs a legend, so one fixed row along the bottom explains whatever cell is clicked — a **strip and not a popover**, because a popover over a 27px cell covers the neighbours you clicked in order to compare, and **always rendered** at a fixed height, because appearing on the first click would shorten the grid under the pointer and move the row being read. Arrow keys move the selection (the useful reading is *across* a row) and skip break and activity columns, which hold no cell; an **empty** cell is selectable, because a free period is a fact. The four facts a placement does not carry — home room, class teacher, weekly cap, curriculum — come from **one** payload (`/context`) fetched beside `/slots`, never a request per click, and are **read off `buildFeasibilitySnapshot`** so the strip cannot disagree with the solver or Readiness; it is cached under the config's slot prefix, which `invalidateTimetable` already sweeps. **A teacher's load names the other wings, never folds them in** — CLAUDE.md's own "67% where the truth is 87%" — and the figure it names is `crossConfigTeacherLoad`, never a second calculation. **Placed against required is drawn ONLY where the two differ** (§31.7, `coverage.ts` in `packages/shared` — one module, so the grid and the strip cannot disagree): a number that is always two numbers is a number nobody reads, and a differing cell drops the subject's colour for signal red because "this row is short" outranks "this is Maths" and the column header still carries the hue. The module exists to be *sure* about a difference — a false one costs the reader's trust in the other 500 cells — so five things are handled by name: **required is a CLASS fact and placed is a SECTION fact** (summing 5-A and 5-B against one class's 6 would report every class as over-taught), §18 extras are excluded by the same `teachingPeriods` set the fill rate uses, a §4.10 merged group **credits both sections** (the one place in §31 merged rows are deliberately not collapsed — `cellEvents` collapses them because a teacher is in one place, here the question is what each class received), a subject that also runs as a §4.9 option is **not comparable** (its option rows belong to no section, so a school holding French as curriculum too would read `0/4` while the children sit in French), and **"nothing placed" is not "nothing generated"** — an ungenerated section is never compared, or a blank screen screams and teaches the reader to ignore the notation. A placed lesson with no curriculum row is out of scope: Readiness owns it. `pnpm test:mastergrid` is the live proof, and the reference school is the scale check — 844 pairs, **zero over-placed**, which is the shape a mis-count would take. **The grid body is windowed with two spacer rows, deliberately NOT `react-window`** (§31.8, `viewport.ts`): 122 teachers x 56 columns is 6,832 `<td>`s, but everything that makes this screen correct is table machinery — the percentage `<colgroup>`, two sticky `colSpan` header rows, a sticky first column — and `react-window` renders positioned divs, so adopting it would trade a working layout for a library that cannot render a `<tr>`. **The row height is measured from a rendered row, never a constant** (§10.6's rule: the spacers must reserve exactly what the undrawn rows would have occupied, or the scrollbar lies). Three frame-level traps, all of them lessons already written down: measure the pane in **`useLayoutEffect`** (§8.1d — a passive effect computes the first frame for a viewport of zero), **seed a fallback height** so the first paint is already windowed rather than drawing all 6,832 cells once and shrinking, and **measure once per layout, not once per scroll** — the ref sits on whichever row is drawn first and that row changes as the window slides, so an unguarded `offsetHeight` there forces a synchronous layout on every scroll frame and undoes the saving. Arrow keys move through the row *list*, so `scrollTopFor` brings an undrawn row into view — to the **bottom** when arrowing down, since jumping it to the top moves everything the reader was comparing it with. Measured: 6,832 → 2,016 cells and 50.8ms → 10.5ms median tree build (**4.8x**); that is `renderToString`, so §14's paint budget stays unverified for this screen — there is no headless browser in the stack. **Two of the six tabs are the real editors, embedded — never rebuilt** (§31.10, §31.11): Lesson grid renders `StepAllocation` and Draft board renders `Board`, each with its toolbar portalled into the host's bar and its cell selection feeding the strip. §31.5's read-only rule was never against editing here, it was against a *second* editor, so it now covers the four pivot tabs only. Three rules the embedding turns on: the **host owns the draft** (two pickers over one screen is two answers to "which draft am I looking at?", so `draftId` goes down and `onDraftChange` comes back up — and the host must refetch the draft LIST as well as its slots, because discarding the server's chosen draft sends `null` and a picker already on `null` changes no URL and refetches nothing); the strip is fed **finished groups from the embedded screen's own payload**, emitted on content and never on identity, or the host's state update re-renders the child that rebuilds them and the loop is armed by any unmemoised value upstream; and the tabs are **permission-gated as props** (`timetable.edit`, `masters.manage`) because a tab must not be a way round what the nav hides. Height is the scarce dimension: the board's five stat boxes moved into the strip, its comparison table REPLACES the grid rather than sitting above it, and its tray is a sticky column beside the grid — a drag target that has scrolled off the top is a drag nobody can finish. Since the four pivots read the host's own copy of `/slots`, the host listens for `slots:changed` too, or a card dragged on the board tab is still in its old cell on Whole.
- **New Timetable is New Wing** (§3.10a). Pressing it creates the `timetable_config`, finishes the guided setup's step 3 and opens **step 4 (Classes)** — a wing has always been a config, so this is a second door onto the same row, not a second flow. `POST /onboarding/session/wing/:id` takes the id in the **path**, not the body, so §17.8's sweep can run it as a controlled experiment instead of accepting a classification; the wing's *name* is read off the row, which is what makes another school's id a 404. Two ways to lose data here: with no draft, `answersFromSchool` must run first or the write becomes that person's first draft row and everything §27.12 rebuilt is gone; and the draft's `session` must name the config's own year or step 4 files class-sections against the wrong session and the new wing looks empty. Which wing step 4 opens on travels in the **URL** (`?at=4&wing=…`) — it is a destination, not an answer, and stored in the draft it would force that tab for ever. `wingRangeFor`/`DEFAULT_WING_SECTIONS` live in `packages/shared` because three doors create a wing and all three used to carry their own `4`, `9` and `2`.
- **One timetable selector, and one timetable at a time** (§30.13). The guided setup had **three** controls for one question — the top bar's *Viewing timetable*, a "Setting up" pool dropdown (§30.9) and a "Teaching" wing tab strip (§32.3) — two inside the page, one above it, and nothing saying which the step obeyed. **The top bar's is the one that stays** (§31.14's argument: it is the control people reach for by memory). `scope` is now **derived** from it, never stored — `allWings` carries `individual` stamped by `stampPools`, so the selected timetable's NAME identifies its pool completely — and switching it clears the error banner and praise line (§30.10). **Every step is handed exactly ONE wing**, which is what removes the strips by construction: each renders only `wings.length > 1`. **Step 3 is the exception and must be** — it is where wings are created, and narrowed to one it could never add a second. The fallback to the whole pool is load-bearing, not a nicety: on a brand-new school nothing is selected because no `timetable_config` exists until step 5, so step 3 calls `refetch()` after `commitWings` or the bar is still empty at step 4. §3.10a's New Timetable now points the **top bar** at its wing rather than a scope of its own. **The bug this nearly shipped with:** `mergeWings` matched on the §30 POOL, which is correct only while a step sees every wing in its pool — handed one, a grouped pool holding Main and New matched both rows, took the incoming wing for the first and `undefined` for the second, and dropped New out of the draft: a **silent deletion of a timetable on any save by a school with two grouped wings**. It merges against the wings the step was SHOWN, by reference (`wingsInScope` is a filter/find over `allWings`, so the objects are the same), staying **positional** because a rename is what a step comes back with. Moved to `packages/shared` as `mergeShownWings` because `apps/web` has no test harness and this function can lose a school's timetable.
- **A class taught by two pools is still ONE curriculum** (§30.12). Since §30.9 two wings in different pools may both run Class 1, so `planClasses` returns one entry **per wing per class** — and everything built by walking that list emitted each shared class twice. `class_subjects` is keyed `(class, subject, year)` with no pool column, so the second copy is *the same row again*; the §16 importer refuses a sheet with two rows on one natural key, and the Master Grid's Save died with **"There are still 322 error(s) — nothing was written"** (209 mappings + 89 curriculum + 24 class teachers — that last being exactly 6 shared classes × 4 sections). The refusal was RIGHT: `sections` in the importer is a `Map<label, id>`, so without it the rows would have been written against an arbitrary one of the two `Class 1-A` rows. **`dedupeCurriculumCells` is the rule and the TIGHTER row wins** — a shared row must fit the narrowest week that teaches the class, or Readiness reports it against a wing nobody was editing. **Deduped in two places on purpose**: `suggestCurriculum`/`suggestMappings` fix what the SCREEN shows (the grid counted 1,168 allocated where the school has 846), and `curriculumSheets`/`mappingSheets` fix what the COMMIT writes — the only gate that always runs, since an edited grid commits from `answers.curriculum`/`answers.mappings` and never touches the suggester. **Never fixed in `planClasses`**: a class taught by two wings in two pools is real and step 4 needs both entries to create both pools' cohorts. Known limitation, stated not hidden: a class-section **label is not unique across pools**, and neither mapping sheet carries a timetable column, so an individual timetable cannot yet be given its own mappings through the guided setup — that is the pool-dimension schema change still outstanding. `pnpm test:pools` drives the real step-9 preview AND commit, because the failure lived in what the server builds from a stored draft.
- **A weekday may run a shape of its own** (§34, `timetable_day_shapes`). A short Saturday — four periods of thirty where the week runs eight of forty — was unsayable, because periods/duration/start all belong to the `timetable_config` and so to every working day at once. **Safe where §28.5 is not, and the key already says why**: `day_of_week` is part of `uq_teacher_slot`, so Saturday's P3 and Monday's P3 are different cells today and nobody is in two days at once — §28.5's collision is *within* a day. That is the second time the answer turned on reading what the index actually compares (§33 was the first): **ask what the unique key compares before refusing on §28.5's authority**. **"Periods a week" stopped being a product** the moment one day could differ, and that product was in Check 1, three branches of teacher capacity, the guided-setup ceiling and the screen — `weekPeriods` in `packages/shared/src/onboarding/week-shape.ts` is the SUM and the only one, with `periodsOn(day)`, `longestDay` (what a per-day cap must be read against — "2 a day" is satisfiable on a full day even when a short Saturday could not hold it) and `halfDayPeriods` (half, **rounded up**: the extra period is easier to remove than to discover is missing). Getting the sum wrong is wrong in the **dangerous direction** — a product over-states capacity, so Check 1 says a curriculum fits when the week cannot hold it. `periodsPerDay` is a SOLVER fact (it prunes periods 5–8 from every domain; `domainFor`'s period loop was already nested in its day loop, so it is one line at the point the structure already provided); `periodDurationMins` is **not** — the solver places into period numbers — but a school saying "half day" means both. Empty = "same as every other day" (invariant 7), and going back to full **deletes the row** rather than storing a copy that would freeze today's count into a day that should follow the week. Asked **where the day was ticked**, **weekend only** (Mon–Fri being full is an assumption every school shares; five more questions nobody has) — though any day whose shape already differs is still shown and editable, which covers one arriving by clone. `pnpm test:dayshapes` asserts the engine's own `totalAvailableSlots` (44, not 48) rather than matching its prose, and that a generation puts nothing past Saturday's ceiling **while a weekday reaches period 8** — the second half is what proves the cap is per day rather than global.
- **A longer lesson is a DOUBLE PERIOD, not a second clock** (§33, `timetable_class_spans`). Class 1 on eight 30-minute periods and Class 10 on four 60-minute ones, same start and finish, is **not** the case §28.5 refuses: §28.5's example is 30 against **40**, which do not line up, so "period 3" means two windows and `uq_teacher_slot` — which compares period NUMBERS — inverts, accepting real collisions and refusing legal ones. **60 is exactly two 30s**, so there is ONE grid of eight 30-minute periods and Class 10's hour occupies two of them. The load-bearing fact is `solver/writer.ts`: a placement of span N emits **N slot rows, one per period number**, so the hour holds period 1 *and* 2 and a teacher also in Class 1's second half-hour is refused — **stricter than the §30 wings route**, where that collision is only a §30.7 warning. `pnpm test:periods` asserts it against MySQL directly rather than trusting the solver not to try. **A span in base periods, never minutes** — the solver wants a block size, and minutes would go stale the moment the config's own duration changed; minutes are what the screen shows (`span × period_duration_mins`), so changing the base moves every class proportionally. Keyed `(config, class)` because the base duration belongs to the config (§28) and §30.9 lets one class sit in two pools. **Empty means "not stated", never span 0** (invariant 7) — bare `CREATE TABLE`, no backfill — and setting it back to 1 **deletes the row**. In `buildFeasibilitySnapshot` it is `Math.max(row.consecutiveBlockSize, span)`: a **floor, never a multiplier**, because a curriculum row's block size is ALREADY in base periods and multiplying would turn an existing double into a quadruple. It sits **behind a link beside the period-duration field**, never a section under it — per-class lengths are the exception rather than the setting, and the table pushed the weekly-capacity note below the fold; the link states its own summary ("2 classes differ") off the SAME fetch the dialog uses, and appears only once the wing is a timetable that teaches somebody. The form offers **lengths, never a free number** (the server sends the multiples that fit the day, so no invalid value is expressible), and **closing time is READ off the `periods` rows**, never recomputed — recomputing would be a second answer and would get §28.4's before-first activity backwards. **The limit**: works when every length is a whole multiple of the shortest — 30/60 is 8 columns, 30/40 needs a 10-minute base and 24, where §30 wings is the better answer and §28.5 stands. Ask a school *"is every period length a multiple of the shortest?"*, not *"do your classes differ?"*. **§33.5 — the week is two columns, not one long stack**: the shape of the day on the left, breaks and activities on the right, and the capacity readout in a strip at the TOP beside the controls that change it (it was last, so the one number the step exists to produce moved while nobody could see it). Four numbers on one line, because "eight forties from eight o'clock" is one sentence and a block label over each made it eight rows. The strip carries **when school closes** via `dayEndsAt` in `packages/shared` — deliberately a SECOND function from the endpoint's `closesAt`, because they answer different questions: the endpoint reads `periods` rows (the authority once written, and it gets §28.4 right), while this answers "what will this be when I press Next?" where no rows exist yet. It returns **null** for a half-typed time rather than a confident "00:40", and never wraps past midnight. **Still to build**: entering curriculum in lessons rather than base periods, warning when a count is not a multiple of the span, and printing a class's week collapsed.
- **A timetable teaches the subjects it DECLARES** (§32, `timetable_subjects`). `subjects` is school-wide and stays that way; what differs between timetables is which of them a week runs. The Subjects step's red **✕** looked like that control and was not — it removed the row from the *draft* while the §16 importer never deletes a subject, so it kept its curriculum, its mappings and its lessons while the screen stopped listing it. **Per `timetable_config`, deliberately not per §30 pool**: two grouped wings share a pool and are the case that motivates it (Junior and Senior teach different subjects out of one resource group). **Empty means "not stated", never "teaches nothing"** (invariant 7) — which is why the migration is a bare `CREATE TABLE` with no backfill. **Selection only**: code, category, priority, placement, lab, own-room and double are one answer per subject, because they describe the subject rather than the week. Enforced in **`buildFeasibilitySnapshot`** and applied to **demand**, not to the subject list, so the rows survive and another timetable teaching the same class the same subject is untouched. **Four carriers of demand, not one** — filtering `class_subjects` alone dropped the `/context` column and the Readiness periods and **generation still placed the subject**, because `solver/variables.ts` builds one variable per **mapping** off `m.periodsPerWeek` while the curriculum row only supplies block size; so mappings, §4.10 merged groups and §4.9 elective **options** are filtered too, the last at the option (a language block minus German still runs) with an option-less block dropped rather than left unsatisfiable. **"All of them" is stored as NOTHING**: the two are indistinguishable today and differ tomorrow, since a subject added later belongs to a timetable that stated nothing and to no timetable that listed every subject it had at the time — so the table records *narrowing*, and a timetable that HAS narrowed does not gain subjects added by another door until somebody ticks them. Unticking the **last** subject is refused (§27.9's rule: `[]` reads back as all). A committed subject has **no ✕** — deselect here, delete on the Subjects master — and the committed set is read from the server, since a draft cannot tell you which of its rows already exist. Not freeze-guarded, matching §29.1's existing exclusion for subjects. `pnpm test:subjects` is the proof, and its load-bearing assertion is a real generation: 8 lessons across 2 subjects where an unfiltered run gives 16 across 4.
- **The guided setup's Classes step cannot describe a smaller school than exists** (§3.10b). It was a pure plan — slider range x "sections per class" — and never asked the database anything. The §16 importer skips by natural key and **has no delete path**, so a screen showing 2 sections for a class that runs 4 created nothing, deleted nothing and reported success: the number was simply believed, while *Remove* and the per-class counter looked destructive and could destroy nothing. **A class's section count is a fact about the SCHOOL**, so the floor is the most sections any one §30 pool runs for it — a timetable may add sections, and may decline to teach the class at all, but never run fewer. That is a rule about the school's record, **not a §30 sharing check**: an individual timetable is floored at 4 *and* gets 4 rows of its own, asserted as one step because the two are easy to conflate. **The floor lives in `planClasses`, never in an `<input min>`** — that function is what the grid draws *and* what `classSheets` turns into importer rows, so a floor the screen showed and the commit ignored is impossible by construction (§10.6's rule in its other form). `GET /onboarding/classes-shape` supplies it, read fresh every call like `stampPools` — a copy of a fact about the school, held in a half-finished draft, goes stale. `SchoolShape` carries two facts that look alike: **`floors` is school-wide** (the widest ONE pool runs, never the total, or an individual timetable is floored at the main school's 4 *plus* its own 2) and **`existing` is per pool**, answering the different question "record or plan?". Both optional — absent means "not stated" (invariant 7) and yields exactly the old behaviour. A class this wing already teaches **loses its Remove button** (it only dropped the class from the *sheet*, so the rows survived and the grid stopped listing children who are still timetabled — deleting a cohort is the Classes master's job, §27.11), and the grid **marks which sections are new**. `defaultSections` is the one definition of "how many sections does this school run?": `recordWing` asked the school, found 4 and never used it, because `answersFromSchool` had already listed the new config as a wing with 2 and the "already in the draft" guard skipped the write — a default with two authors has one that wins silently. `pnpm test:classfloor` is the proof.
- **Cloning a timetable copies the inputs, never the outputs** (§3.12): settings, periods, class-sections, curriculum, mappings, merged groups and elective blocks come across; `timetable_slots`, drafts, publications and §18 extra classes deliberately do not — the admin adjusts and presses Generate, which also keeps the whole feature clear of the §22 `draft_scope` unique keys. Always into a **different** academic session (a class-section belongs to one session and one timetable, so the same session cannot hold two copies); named drafts are the tool for alternative *placements* within a session. Preview writes nothing, not even the target year. Inactive and `guest` teachers are dropped **and named** — the curriculum still records the demand, so Readiness reports the gap instead of Generate failing. Since a clone is what makes duplicate-looking rows normal, `GET /class-subjects`, `/mappings` and `/elective-blocks` all take an optional `academicYearId`, supplied by the screen from the chosen timetable — never a second selector.
- **Teacher availability is a hard constraint with a screen** (§4.7a, `/availability` under Build). `teacher_unavailability` is one row per blocked cell, `period_number = NULL` meaning the whole day; the solver prunes those cells from the teacher's domain *before search*, the board refuses a drag into them, Check 2 subtracts them from weekly capacity, and the substitute engine drops the teacher from the candidate list rather than scoring them down. The screen's quick patterns (arrives-after, leaves-by, second-half, whole-day) are **entry shortcuts that compile to cells** — never a second rule model. A day with every period blocked is stored as one NULL-period row, so it survives the timetable gaining a period.
- **A commit is not only a create** (§16.1). The §16 importer skips existing rows by natural key — but it also **links rows that already exist**, and none of those links are part of a key: a class-section to its timetable, a lab to its subjects (§19.1), a teacher to what they teach (§27.13). So `commitSheets` must not return early when `create === 0`; it did, and a school with every class entered and both wings created sat at `timetable_config_id = NULL` on all 32 sections with Readiness at 0% and a message saying everything already existed. Filling a NULL link is the §21 `complete` shape and is allowed; **overwriting a link that has an answer is not** — a section already in another wing stays there (invariant 11).
- **Time off is four tables and one screen** (§4.7b). A class, a subject and a room each get the teachers' §4.7a grid — three tables mirroring `teacher_unavailability`, never one polymorphic table (an `entity_id` costs the foreign key and leaves the §23 cascades unable to name what they delete). The sameness lives in `feasibility/time-off.ts`, the one definition of **"`period_number` NULL means the whole day"**, read by the solver, the board and the engine. **Class time off makes the week SMALLER** — Check 1 subtracts it, or Readiness reports 100% on a school whose curriculum no longer fits and the solver takes the blame. A blocked room is written into `SolverState`'s occupancy map at construction, so all five room-picking branches are correct at once rather than each needing a fourth condition. Two states, hard: "conditional" is a soft preference and therefore a §5.6 scoring term, not an availability state.
- **The selected Lesson Grid cell IS a field** (§31.16) — a real `<input>`, so `CellShell` renders a `<button>` normally and a `<div>` when selected (an input inside a button is invalid HTML and the button eats the click that places the caret); one shared style object, no invented ARIA role on the div. The typed value is a **string**: bound to the number, deleting the last digit would put `0` back under the caret and "12" would read as "012", so an empty field writes nothing rather than zero. **Arrows move cells, not the caret** — the window handler ignores a focused input by design, so navigation lives in the field, and focus follows the selection in a **`useLayoutEffect`** or the caret lands a frame late on every move. **Backspace no longer removes a subject** — conditional meaning by caret position is the worst possible binding for a destructive action; `Delete` keeps it, and Escape blurs *without* clearing the selection, which also draws the toolbar. The Periods field left the bar: two boxes for one number is two answers to "where do I change this?", and the far one wins by being easier to see.
- **The Lesson Grid edits in the toolbar, not in a popup** (§31.15). A click SELECTS; the number is typed into the cell (digits **accumulate** within 900ms — each press used to replace the value, so "12" ended as 2 and ten was unreachable); every other field lives in `CellBar` in the bar the filter is in. **No Save in the bar** — the dialog had one because it batched fields behind a confirmation, and a toolbar that confirmed each field would be a dialog in another shape; edits land in the draft as made, and the Master Grid's Save writes them. `applyCell` is the ONE definition of what a `CellSave` does (periods before block, or a cell this save created has no row for the block) and both doors call it. The dialog survives behind **Enter** / **⋯ More** for the two things a bar cannot hold: the whole-week impact preview and §4.10 merged-group members. Start again, Clear saved data, Hover detail and Help are in a `<details>` hamburger — pressed once in the life of a school, and taking width the grid wants. The selection is cleared on a wing change (a bar that edits must not point at a hidden section) and the block control is disabled at zero periods (`setBlock` returns early with no curriculum row).
- **The guided setup has no Allocation step, and every step it does have is reachable** (§31.13). Rooms → Settings, and Settings carries a button to the Master Grid's Lesson Grid — the same `StepAllocation`, so nothing was rebuilt. **The step NUMBERS did not change**: `WIZARD_STEPS = [1..8, 10]` says which steps are *shown*, so `POST /onboarding/commit/:step`, the stored `current_step`, `migrateStep` and `ALLOCATION_STEP` all still mean what they meant, and a draft saved on step 9 resumes on Settings via `visibleStep`. The wizard therefore never commits the allocation — the Lesson Grid's Save does, which is the same `commitAllocation`. The rail no longer locks a step behind its predecessors: a forward jump **commits what is ready, skips what is not, and always lands**, naming the skips (every commit is idempotent, so a later Next writes exactly what the jump did not); `problemAt` still guards Next, and an unfinished step gets an amber ring rather than a lock. **The Lesson Grid has no draft picker, status select or draft chip** — curriculum and mappings are master rows every draft is generated *from*, so a picker there would imply "Class 5-A gets 6 periods of Maths" could differ between drafts; the other four tabs are placements and keep all three. **The assistant's launcher lives in `Shell`'s top bar on every page** (§31.14) — it floated in the corner, where it covered the Master Grid's issue count, and docking it in that one screen's bar put a control people reach for by memory in a different place on one page out of thirty; the floating button remains only as the fallback for anything outside the shell, and the panel's `top` is measured rather than constant because a §30.5 dated timetable makes the top bar taller. A label bug rode along with §31.13: the Next button read `STEP_TITLES[step]` — the title one index along, correct only while the sequence was 1..10 — so Rooms offered "Next: Allocation" and landed on Settings; it reads `stepAfter(step)` now, the same function the press uses. **Allocation Matrix and Draft Board left the nav** (they are Master Grid tabs) while their routes stay, because Generate and Publish link to them and people bookmark screens; Master Grid moved to Build directly below Masters, and `/allocation` redirects to `/master-grid?tab=lesson`.
- **The masters live on `/masters`, not in a wizard** (§8.2). A wizard is a sequence; masters are a set. The five master steps moved there unchanged, curriculum and mapping are the Allocation page, and `/setup` keeps only the timetable's own week (period grid, breaks, §28 activities, which sections a wing covers) — those are facts about one timetable, not about the school. The per-class **Lessons** view is read-only on purpose: the Allocation grid is the one writer for curriculum and mappings, and it must ask §4.9 blocks for their options or a language block renders as a free period (invariant 9). The welcome screen has two doors, not three — manual entry was a third writer over rows two paths already own.
- **The Extra & Guest Classes screen is under Manage** (`/extra-classes`), beside Substitute Center. Blocked until the timetable has an extra window, and it says so rather than offering an impossible form.
- **A full test school is generated, not typed:** `docker compose exec api node /app/scripts/seed-school2.cjs` builds Second Branch — 14 classes x 4 sections, 122 teachers, 8 split-elective language blocks, 100% readiness, 2,240 periods. The curricula in `scripts/school2-model.cjs` are the only hand-written numbers; demand, staffing and mappings are derived from them. Add `--dry-run` to see the plan without importing.
- **Tenancy has one gate: `pnpm test:isolation`** (§17.8, in-container). Its sweep asks the running app for its route table (`GET /dev/routes`, dev-only) and **requires every route to be swept or explicitly classified** — so a new controller fails the build until somebody decides which. Each route is tested as a controlled experiment: same URL, same body, once per school, and both a refusal for the stranger *and* a different answer for the owner are required — a route that refuses everyone proves nothing and is reported as such, never counted as a pass. Never replace this with a hand-written endpoint list; that is precisely the thing it exists not to be.
- **`WORKER_LOCK_DURATION_MS` is 5 minutes, not BullMQ's 30-second default** (§17.7). A synchronous solve blocks the event loop, so the lock-renewal timer never fires and a healthy job goes "stalled" — then runs twice. Never lower it below the solver budget, and keep it under the 15-minute per-school slot TTL.
- **Another school's id is `404`, never a successful no-op.** A scoped `updateMany`/`deleteMany` that matches nothing must not answer `{ok: true}`: it is indistinguishable from the outside from a real write, and becomes one the moment someone swaps in `update`. Check ownership explicitly, then act.
- **`docker compose up` starts a second MySQL server (`mysql-b`, dev-only) with its own credentials**, and a school is provisioned onto it by the isolation suite. A second *database on the same server* cannot catch a routing bug that falls back to the default connection; a different host with a user that exists nowhere else can.
- **Every log line is tagged with its school automatically** by `TenantAwareLogger` — never hand-add a school id to a log message; just log, and the ambient context supplies it.
- **Platform administration is not a school permission** (§17.6): it lives in the control plane's `platform_users`, keyed by ERP identity, because a school's own Super Admin must not be able to grant themselves authority over the registry. Never add a `platform.*` entry to the §15.2 permission registry. It is re-checked per request (not carried in the session token, which would keep saying yes for 8 hours after a revocation), and granted by `pnpm --filter @edutimetable/api platform:admin -- --grant <ERP-USER-ID>`.
- **The ERP master-data sync reads a REST API only, one master at a time** (§23). Endpoints and field names are *described* in `ERP_API_FILE` (template: `scripts/erp-api.example.json`), never coded — a master with no entry is "not configured" on its own card and blocks nothing else, and there are no built-in default paths because a guess that 404s reads as "the ERP is broken". Dev runs a stand-in: the `erp-fake` compose service over the `erp_fixture` database, reached over HTTP with a token exactly as production would. **Deleting is allowed and is counted first:** `timetable_slots` has no foreign keys to the masters, so a removal is invisible to the database — `apps/api/src/sync/dependencies.ts` owns the cascade, and each step declares its *count and its delete in one object* so the confirmation can never under-report the write. Never add a nested relation filter from `timetableSlot` to a master; there is no relation. The sync clears `users.teacher_id` rather than leaving it aimed at a reusable id, and **never deletes a `timetable_config`** — where a removal would need to, it refuses and names it. `refresh` (key-preserving) is the default; `replace` re-mints every id and is a first-load tool. Every run lands in `erp_sync_runs`, failures and refusals included. **Authentication is described in the same file** (§23.8, `erp-auth.ts`): `oauth2` client credentials by default, and the secret lives in the env var the `auth` block *names* — never in the file, which is committed, and never in an error message, which is rendered on screen and logged. **Never try to authenticate to the ERP with its own SSO token** — it is single-use, short-lived and discarded at login; what is forwarded instead is `actingUserHeader`, the ERP id of whoever pressed Sync, absent on an unattended run. A 401 refreshes the token and retries exactly once, never in a loop.
- **Socket.IO handlers must open their own tenant context** (§17): a socket message never passes through the HTTP middleware, so nothing has scoped it. `AiChatGateway` opens one from the signed session token before touching the database; any new gateway must do the same or its queries run unscoped — and, for a school with its own database, against the wrong one.
- **LLM providers sit behind one neutral contract** (`apps/api/src/ai/providers/`, §13.2): the chat gateway never speaks a vendor's message shape. **Anthropic (Claude) and Google (Gemini) are both wired**; `providers/index.ts` is the single catalogue of providers, models, env-var fallbacks and prices, served to the UI so the screen cannot drift from the gateway. Adding a provider = an adapter + one catalogue entry, never a change to the chat loop or the §13.1 tool registry.
- **LLM usage is deliberately narrow:** never for slot placement (it can hallucinate invalid placements). Only for plain-English explanation of constraint failures, natural-language bulk data entry (with confirmation screen), and substitute-suggestion rationale text.

## Non-negotiable invariants

1. **DB-level uniqueness is the final guard against double-booking** — three unique keys on `timetable_slots`: `uq_class_slot`, `uq_teacher_slot` (via generated `teacher_occupancy_key`, which collapses merged-group placements into one occupancy event), and `uq_room_slot`. App-level checks are additional, never a replacement.
2. **Teacher placement rules are HARD constraints, never soft preferences.** `class_teacher_period_rule` (`always_first_period`), `period_pattern` (`alternate_period`, `alternate_day`) are enforced by **domain pruning before search starts**, not penalty scoring. The solver must never be able to even consider an illegal slot.
3. **Draft vs. published lives in one table** (`timetable_slots.status` enum), not two tables — so unique constraints, solver, and drag-drop UI all work against one schema. Publish is a single transaction. **A config has several named drafts** (§22, Phase 17): `timetable_drafts` is the registry and `timetable_slots.draft_id` the scope, with a MySQL **stored generated `draft_scope`** inside all three unique keys — `0` for published and `source='extra'` rows, the draft id otherwise. That collapse is the whole design: one published set per config however many drafts it was promoted from, extras once per config, but Draft #1 and #2 may both put a teacher in Monday P3. Never write `draft_scope` from code (Prisma needs `@default(dbgenerated())`, or it sends the column and MySQL rejects the insert), and **never build a slot row without a `draftId`** — `swap`, `swapGroup` and `place` all rebuild rows field by field, and a missed `draft_id` silently drops the card into scope 0, outside every draft. Reads default to the config's current draft — **the newest one that has rows**, so pressing Generate does not blank the board while the worker fills the new draft. A single-draft school is unaffected. Anything cached per timetable is swept by **prefix** (`configSlotsKeyPattern`), never by naming keys: the suffix is open-ended now (`slots:119:draft:d7`, `ctx:d7`), and three hand-written deletes left every per-draft copy stale. `scanDel` is one shared implementation because the BullMQ worker has no Nest context and a second copy would drift. **Multiple named drafts (§22) are a scope, not a second table:** `timetable_drafts` is a registry with per-draft stats, and the generated `draft_scope` column (published and `source='extra'` rows collapse to `0`; each draft keeps its own id) joins the three unique keys — so two drafts may hold alternative placements while two published sets remain impossible. Stats (generation %, required/placed lessons, errors) are stamped on the registry row via Check 1's own arithmetic and `SolverState.check()` — never recounted ad hoc at render time.
4. **Substitutions are date-specific overlays** (`source='substitute'`, logged in `substitution_log`), never mutations of the base published timetable.
5. **Rooms are assigned, not left blank** (§19). The solver claims a class-section's `homeRoomId` for every non-lab lesson — before Phase 12 it wrote `room_id = NULL` and the recorded home room did nothing. A lab subject draws only from labs mapped to it via `room_subjects`; **a lab with no subjects listed is general and serves everything**, which is what keeps pre-§19 schools working — never "tidy that up" by requiring the mapping. One room, one home class-section: Check 9 blocks a shared one because both are timetabled all week.
5a. **A subject may be taught in its own room, and the flag says WHETHER while `room_subjects` says WHERE** (§19.1). `subjects.taught_in_own_room` is one boolean with deliberately no room id beside it: `room_subjects` has meant "this room serves these subjects" since §19, and a second column would be a second answer to "where does Music happen?" — free to disagree, and unable to describe a school with two music rooms. The room ladder is `preferred_room` → **the subject's own rooms** → the lab pool → the home room; own-room sits above labs because a school that names the room is being narrower, and the lab branch would widen it back to every general lab. **Ticked with no room named is "not stated", never "anywhere"** — the lesson takes the home room and Check 5b warns, because scattering the subject through whatever was free is the opposite of what the tick asked for. Check 5b is **per subject** (two music rooms and a pottery room are not interchangeable capacity) and blocks before Generate, naming the room.
6. **A teacher's day is bounded at both ends** (§20). `min_periods_per_day` (default 3) means **zero or at least N** — never "at least N every day", which no part-time teacher could satisfy. The number actually enforced is clipped by the teacher's weekly load *and* their **daily reach** (Σ of their subjects' own per-day caps): a teacher running one class's 1-a-day language block can never have 3, and demanding it would make the school unsolvable. One module owns that arithmetic (`feasibility/min-day.ts`) — never re-derive it at a call site. It is a lower bound, so it is enforced as a *budget* (shortfall owed to started days ≤ periods left to place), not a per-placement veto. **Completeness outranks shape:** if the enforced pass leaves lessons unplaced the solver falls back to the exact pre-§20 search and reports `stats.shortTeacherDays` — never ship a change that trades placed lessons for a tidier week. On the board it is a warning, not a refusal.
7. **A teacher may only take the classes they are eligible for** (§18). `teacher_class_eligibility` is *declared*, not derived — the pre-Phase-11 grade band came from existing mappings and so could never constrain them. Enforce through `masters/teacher-scope.util.ts` at every attachment point (mappings, merged groups, elective options, class teacher, importer); Feasibility Check 8 is the backstop for data those paths never saw. An empty scope means "not stated", never "no classes". A `guest` teacher is refused the regular curriculum entirely and is never offered as a substitute.
8. **Extra classes live in the config's extra window, never in the teaching day** (§18). `extraPeriodsPerDay` appends periods after the day; the solver only reaches `1..periodsPerDay`, so it cannot place there — do not "fix" that by widening its domain. They are `timetable_slots` rows with `source='extra'` in *both* statuses, and regeneration, publish and draft-from-published all deliberately skip them: re-running the solver does not cancel next week's revision class.
9. **Split electives are one slot, several lessons** (§4.9, Phase 10). A block's *member* rows (one per attending section) carry the block and no subject/teacher/room; its *option* rows carry `class_section_id = NULL` plus their own teacher and room. Never "fix" that NULL — it is what takes option rows out of `uq_class_slot` while leaving `uq_teacher_slot`/`uq_room_slot` guarding them. Code that means "a grid cell" (board, publish diff, matrix, locked slots) filters `classSectionId !== null`; code that means "a lesson" (teacher timetable, substitute plan) keeps them, labelled by their block. **That filter belongs at the consumer, never at the transport:** `GET /slots` serves both the By Class-Section grid (cells) and the By Teacher grid (lessons), and filtering once at the source made every elective-only teacher — nine of them in the reference school — look entirely unscheduled on the Matrix and the Board. A payload serving both meanings carries both. **A block is a draggable card (Phase 16) and moves as one unit** — every option row and every member section together. `BoardEngine.varOf` emits the real §4.9 macro-variable so `SolverState` does the checking; never re-implement those rules on the board. A multi-section card (block *or* merged group) uses `checkSwapGroup`, not `checkMove`: it can displace a different lesson in each member section, and a plain move would need every member cell free at once, which in a full school never happens. A swap with another occurrence of the same block is refused — it changes nothing, and on the reference school it was otherwise every "legal" destination a block had. A block carries no 📌 (`lockedSlots` filters to rows with a section, subject and teacher, so a pin would be silently ignored by the next Generate — `placement: fixed` is the real tool) and no ✕ (the tray is mapping demand; a block is not a mapping). **A third language is this construct, not a new one:** 5-A, 5-B and 5-C keeping Monday P4 open while French, Sanskrit and German run inside it under three teachers in three rooms is exactly a block with three member sections and three options — never model it as three mappings. Because a member row is deliberately empty, **anything rendering a class's week must ask the block for its options** or the period reads as free; `ReportsService.classSectionTimetable` does it once and My Classes, the CSV export and the AI tools inherit it. **`placement` (§4.9, Phase 15) is domain pruning, never scoring** — `same_period` reuses the existing `samePeriodKey`; `fixed` hands occurrence *i* its pinned cell. Check 7b names every bad pin before Generate, and every one of its remedies hands the block back to the solver: auto-resolve may turn a pin off, never move a block to a day nobody chose (`fixedSlots` is deliberately absent from the auto-fix `WRITABLE` list).
10. **Multi-block placements are macro-variables:** double periods (`consecutive_block_size`), merged teaching groups (one teacher, multiple sections at once), and split electives (synchronized parallel options) each place atomically — fully placed or fully backtracked, never half-placed.
11. **A class-section belongs to exactly one `timetable_config`** (a school runs multiple independent timetables per wing), but teacher load checks sum **across all configs in the same academic year** a teacher appears in — cross-wing overload must never slip through, while next session's teaching must never consume this session's capacity. **The curriculum is year-scoped too** (§3.11): `class_subjects` is keyed `(class_id, subject_id, academic_year_id)`, and `buildFeasibilitySnapshot` filters it to the config's own year — that one filter is why the engines need no year of their own, since `solver/variables.ts` keys requirements by `classId:subjectId` in a plain Map and two sessions' rows would collapse to whichever loaded last. The year is **required on write and never inferred from the active year** (a row filed against the wrong session is invisible until the timetable comes out wrong) but optional on read. Never re-derive a class's weekly capacity without its year: a class has sections in every session it has ever run.
12. **Drag-and-drop is validated twice:** client-side instantly (in-memory matrix copy), then server-side on drop-confirm (guards against stale/concurrent edits). Illegal drops show the *specific* reason. Picking up a card highlights every legal destination.
13. **Manually placed cells can be locked** (`is_locked`) — solver re-runs must treat them as fixed.
14. **The AI Assistant is tool-gated, and the LLM never writes** (§13). It answers only through whitelisted tools that wrap the Reports module's service functions — never raw SQL, never table dumps, **never slot placement**. Since §13.5 it may also *draft* master data (`draftMasterData`): it proposes rows, the §16 `validateWorkbook` checks them by exactly the rules an Excel upload gets, and the write happens only when a human presses Apply. That distinction is the whole safety argument — **the model proposes, a person disposes, and the existing validated committer does the writing**. Never add a tool that writes directly. The drafting tool needs `masters.manage` (not a new AI permission — the authority to add a teacher is the one the Setup Wizard already requires), is limited to seven masters, and can never delete or touch a timetable. Apply takes a *proposal id*, never rows: the batch lives in a school-keyed Redis stash, is re-validated at the moment of the write, and is single-use so a refresh cannot double-write. Phase B lets it **change** existing rows, under two rules that are easy to get wrong: the **natural key is never writable** (a changed key is a new row, not a rename), and **a field the draft did not mention is not a change** — `validateWorkbook` returns a fully-defaulted row, so diffing against it would null every untouched column; the adapter's `mentioned` list is what says which fields were actually asked for. **`Subject Mapping` is the sheet where one drafted row is not one database row** — it fans out to one mapping per class-section, or collapses into a merged group — so it is expanded by `data-entry.mapping.ts` (the importer's own expansion, never a second copy) before anything is diffed. The key differs per unit, and so does the answer: a plain mapping is keyed `(subject, class-section)` so the **teacher is a value** ("move Class 5-A maths to Rekha" is an edit); a merged group is keyed `(subject, teacher, members)` so the teacher is **identity** and a draft that moves it is refused by name — otherwise the importer would create a second group over the same children. The §18 and weekly-capacity guards run at plan time *and* at apply, reusing `assertCanTeach`/`assertWithinWeek` — a conversation is never a way round a rule the screen enforces. School/timetable scope is injected server-side into every tool call.
15. **Performance budget — every transactional page and on-screen report ≤ 1s at p95** (§14): API ≤ 300ms (DB query ≤ 100ms), client render-to-usable ≤ 600ms, at realistic scale (50 sections, 2,000 slots, ~40 concurrent users). Achieved by: heavy work off the request path (BullMQ), mandatory indexes (`EXPLAIN`-checked, no full scans on `timetable_slots`), Redis caching with event-driven invalidation for computed views (readiness, published matrix, report aggregates), virtualized grids, paginated compact payloads (no N+1, no nested ORM graphs), client-first drag-drop legality. The only sanctioned exception: PDF/Excel *file generation* and AI chat totals may exceed 1s but must acknowledge/start within 1s (queued job + progress). CI load tests assert the budgets — a perf regression fails the pipeline like a failing test.
16. **Two ways in, one session token, app-wide RBAC, query-layer view scoping** (§15). ERP customers arrive from the Edunext menu via a short-lived signed SSO token (verified, nonce-replay-protected, sync-on-login provisioning). Since Phase 25.0 a school that bought only the Timetable module can also **register locally** — and the containment rules matter more than the feature: **credentials live once, in the control plane** (`accounts`, beside `platform_users`), never in a tenant database, because one person may run several schools and `users` is one row *per school*. Local sign-in issues **exactly** the `SessionTokenPayload` the SSO callback issues, so every guard, scope filter and audit path is untouched. An account that has not yet entered a school holds an `AccountTokenPayload` instead — a deliberately tiny credential reaching only `/auth/account` and (25.1) the school list — and `JwtAuthGuard` **must refuse it**, since it carries no `schoolId` and would otherwise bind an undefined school. Never add a password column to `users`; never let an ERP user acquire one. One permission registry (`roles`/`role_permissions`) covers the entire app; the Admin manages it on the dedicated Roles & Responsibility page (`roles.manage`). The three view levels (`timetable.view.own` / `.class` / `.all`) are **row-level scope filters injected server-side into every query** (REST, Socket.IO, reports, AI tools — one scoping module) — a teacher gets only their own grid and their linked class-sections' grids; UI hiding is cosmetic, the server is the authority.
17. **The ERP owns school identity — never hardcode or invent a school name** (§15.1, §17.4). The SSO token carries `school` (`code` + `name`), optionally `trust` and `schools[]`; the app provisions unknown schools on the spot (row + permission registry + ERP role mappings + registry entry) and refreshes names on every login. `code` is the stable key across databases — a numeric id is not. School switching is authorised by the signed session token's `schoolIds`, never by a permission, and the school always comes from the session, never from a request body.
18. **Row ownership is scoped in one place, and `school_id` is on every table** (§17, Phase 9.1). All 30 tables carry `school_id` — denormalized onto child tables so scoping is always a direct indexed predicate, never a join. One Prisma client extension (`apps/api/src/prisma/school-scope.ts`) applies the ambient school from an `AsyncLocalStorage` tenant context to **every** query: filters reads, stamps creates (recursively through nested relation writes), refuses updates/deletes of another school's rows, and rejects writes that *reference* another school's ids. Never hand-add a `schoolId` filter at a call site as the mechanism — a query is scoped by the context it runs in. Never use Nest request-scoped providers for tenancy (it cascades through ~40 injecting classes and breaks the §14 budget). Redis keys are `s{schoolId}:…`, Socket.IO emits go to a `school:{id}` room — never `server.emit` — and every BullMQ job carries its `schoolId`. `PrismaBaseService` and `TenantContextService.runUnscoped()` are the only sanctioned ways out, for genuinely cross-school work (health probe, migrations, SSO provisioning). Since 9.2 every `school_id` also has a real **foreign key** to `schools`, and `schools` itself is the tenant *root* — scoped by its own `id`, never stamped, never created or deleted from inside a school's session (that is provisioning, §17.3).
19. **Auto-resolve may complete or redistribute, never loosen** (§21, Phase 14). The Feasibility Engine emits a structured `remedy` beside the human `fix` string — never parse the prose. Remedies are `complete` (fill in what is unstated), `redistribute` (move teaching to somebody with room) or `relax` (raise a cap, lower a floor); only the first two are ever applied by a standing consent, because a resolver free to loosen limits can take any school to a Readiness Score of 100 without changing one real thing; `relax` is always shown first as one priced, grouped card. A relax remedy changes the *rule*, never what children are taught or who is responsible for them - turn the same-period rule off rather than cut a subject's periods; set a Period-1 rule to `random` rather than take a class teacher off a section; shorten a block rather than move a break that lands on every class in the school. The server re-runs the engine and applies **only its own current remedies**, matched against what the admin consented to — the request is never the source of the writes — bounded further by the `WRITABLE` field allow-list, and every change is compare-and-set on the value the admin saw. **Fixed is a verdict, not a claim:** an issue counts as resolved only when a re-run no longer reports it. Every run is undoable from `auto_fix_runs`.
20. **AI access is role-based and server-enforced:** `ai.chat`, `ai.reports`, `ai.configure` permissions checked by middleware on every AI endpoint (REST + Socket.IO chat namespace) — hiding nav items is cosmetic, the guard lives on the server. API keys are AES-encrypted at rest, write-only in the UI, and every conversation is audit-logged (`ai_chat_log`) with token usage counted against a monthly budget.

## Feasibility Engine — the six checks (§4 of the architecture doc)

1. Slot capacity per class-section (required vs. available slots)
2. Teacher weekly load vs. true capacity (pattern-adjusted for alternate-period/day teachers)
3. Daily distribution feasibility (`periods_per_week` vs `max_periods_per_day`, block-packing-aware)
4. Teacher cross-section daily overlap / tightness score
5. Shared/special room contention
6. Structural constraint conflicts (e.g., class-teacher P1 deadlocks, underspecified same-period-across-week rules)

Every failed check maps to a **specific, actionable message naming the exact row and fix** — this "tell me what to fix" intelligence is a core product requirement, not polish.

## UI design system (from `timetable-ui-mockup.html`)

- **Fonts:** Fraunces (display), Inter (body), JetBrains Mono (code/data) via Google Fonts.
- **Palette (CSS variables):** dynamic-blue theme — primary `--brand:#2563EB` / `--brand-dark:#1E4FC4` / `--brand-deep:#0B1F44` (sidebar navy), muted blue-gray `--steel:#5578A8` / `--steel-light:#B6CBE8` / `--steel-pale:#E7EEFA`, surfaces `--offwhite:#F4F7FC` / `--line:#DBE3F0`, ink `#141B26/#4F5D70/#8695A9`, error `--signal:#C2372F`, warn `--amber:#B9791A`, success/positive `--accent:#0891B2` (cyan). Never reintroduce the retired forest/sage/mint green tokens; new UI must use these variables, not hardcoded colors.
- **Subject and class colours come from one module** (`packages/shared/src/colors/palette.ts`, §10.5) — never derive a colour at a call site, or Maths ends up green on the Board and blue on the Matrix, which teaches the reader something untrue. 32 swatches (16 hues × 2 tones); each is a light fill plus text that is a **dark shade of the same hue**, every pair ≥ 4.5:1 on its own background *and* on white, enforced by `palette.spec.ts` recomputing the ratios rather than trusting a comment. The assignment is **set-aware** (`assignSwatches`: hash to a preferred slot, probe forward, names sorted) because a bare hash leaves ~5 of 20 subjects sharing — the birthday problem, not a small palette. Served by `GET /me/colors` (session only, names + ids) so a teacher and an admin see the same scheme; `/subjects` and `/classes` are `masters.manage` and would give a teacher a 403. Colour the thing the cell is *about*: subject in a class grid, class in a teacher grid, keyed on the class so 5-A/5-B/5-C are one family. **Existing meanings outrank colour** — substitution keeps its cyan, a pin keeps the grey locked fill, a §4.9 block keeps its dashed steel tint in a class row (it is several subjects at once) but takes its option's real colour in a teacher row.
- **Layout:** dark navy sidebar (236px) + top bar with a timetable-config selector; screens: Timetables (landing), Setup Wizard (stepper: Academic Year → Classes/Sections → Rooms → Subjects → Teachers → Timetable Config → Curriculum → Teacher Mapping → Electives — capacity-first: the config's weekly period count hard-caps every later periods/week entry), Readiness Dashboard, Generate (live progress log), Allocation Matrix (sticky headers/first column), Drag-Drop Board, Publish Confirmation, Substitute Center, Reports, Masters, Notifications, (role-gated, under an "Intelligence" nav group) Ask AI chat + AI Settings, (Admin-only) School Profile + Roles & Access, and (platform-only) the Platform Console. Teacher-role users get scoped My Timetable / My Classes views instead of the admin screens.
- **Split Electives** (`/electives`, and the wizard's last step) is the only way in the UI to build a third-language block — before Phase 15 the model, solver and six feasibility checks existed with no screen, reachable only through the Excel importer. The form is block → member sections → N options (subject + teacher + room each) → when it runs.
- **The guided setup's Curriculum and Mapping steps are one Allocation grid** (§27, `steps/Allocation.tsx`) — class-sections down, subjects across, three facts per cell. Two rules it must keep saying out loud: **periods are a *class* fact** (`class_subjects` is keyed by class, so the Load column spans the class group and the dialog says so) while teacher and room are *section* facts; and the load arithmetic is **not a second opinion** — `computeLoads`/`relieveLoad` live in `packages/shared/src/onboarding/load.ts` and the server calls the same functions, which is what retired the older "don't second-guess `assertWithinWeek`" rule rather than breaking it. A **merged group costs its teacher one lesson, not one per section** (§4.10) — get that wrong and the advisor's own merge suggestion appears to change nothing. Merging is offered **only for co-scholastic subjects**; `relax` remedies are always last, priced, and never automatic (invariant 19). Period *length* is a wing fact (`timetable_config.period_duration_mins`), shown and edited here but committed through step 5's own `commitWeeks(answers, {changedOnly:true})` — never through the §16 importer, and never unconditionally, because `PUT /:id/structure` rewrites the period grid wholesale. The wizard has **ten** steps; a stored `currentStep` is read through `migrateStep`, since old step 10 (Mapping) collides with new step 10 (Settings).
- **Three generation settings, and one deliberately missing** (§28, Phase 29). `timetable_config.load_alert_pct` (default 75) is the line at which the app says a teacher is getting full — **a warning, never a blocker, and exempt from the readiness score**: a school that asks to be told when somebody passes 75% has not become less able to generate by asking, and a dashboard falling to 98% for answering reads as the setting having broken something. Feasibility **Check 12** reports it as ONE grouped row with no remedy (every way to lower the number is either a `redistribute` the §27 advisor already offers or a `relax` that raises the very cap it is measured against). **Daily activities** (`daily_activities`, §28.3/28.4) are assembly/attendance/dispersal — one table for both ends of the day, producing a third band in `periods` beside break and extra. They are cheap for exactly one reason: **an activity has no period number**, so `domainFor` cannot reach it, the same device the §18 extra window uses — never widen the domain to include them. A before-first activity makes the day start **earlier**; it never pushes period 1 later, because `startTime` is what is printed on the wall. `daySegmentsFromRows`/`lunchAfterPeriodFromRows` must **exclude** activity rows: an activity is not a break, so without the filter the run counter reads an assembly as a teaching period. **Per-class period duration is NOT supported and must not be added cheaply** (§28.5): two period lengths in one config make a teacher's Class 9 P3 overlap their Class 11 P2 in wall clock, and `uq_teacher_slot` compares period *numbers* — invariant 1's database guard silently stops guarding. The real design is tick-based occupancy; until then, a different period length is a different wing.
- **A teacher's classes are declared on the Teachers step** (§27.9), and `suggestMappings`, the Allocation dropdown and `relieveLoad` all honour them — a rule enforced in only some of those is one a school finds by being contradicted. Every class is ticked by default and removal is the interaction, but **`classes: []` is what gets stored while nothing has been removed**: empty means *not stated* (invariant 7) and falls back to the wing, which is also what makes a teacher who changes wing follow the new one. The **last class cannot be removed** — that would store `[]`, which means *all*, so taking one away would hand them every class in the wing.
- **Every suggested step needs a way back to the suggestion** (§27.10). The Allocation grid stores its plan the moment it is edited and the stored plan then wins for ever — so without a reset, changing the Teachers step leaves the grid unmoved, which reads as the page ignoring you. Clearing sends **`null`, never `undefined`**: the wizard sends only touched keys and `JSON.stringify` drops undefined, so the server merges nothing and the edit survives a reset that appeared to work. `edited()` reads any non-array as "not stated" and re-proposes. Note the limit: the §16 importer skips by natural key, so a mapping already committed keeps its teacher — re-staffing changes the draft, not committed rows.
- **Clearing the allocation is a deletion, not a re-proposal** (§27.11, `allocation-reset.ts`). Two controls with different meanings: *Start again* rebuilds the draft from the suggestion and touches no saved row; *Clear saved data* deletes the curriculum, the mappings, the class teachers and the draft rows built from them. Built like §3.13's config deletion — **count and delete declared in one object** so the confirmation cannot under-report, plan recomputed server-side, and a **published timetable refused on the write as well as in the preview** (its slots would outlive the reasons for them). Curriculum is deleted by class **and academic year** (§3.11) or it takes another session's planning; a merged group is this timetable's only when **every** member is, since `merged_teaching_groups` has no config FK; §4.9 elective blocks are counted and named, never removed — they belong to the Electives screen. Confirmation is a typed word, because every count is a row somebody entered.
- **A master is entered once and used for ever** (§27.12). Deleting a timetable removes slots, drafts, periods and publications and **detaches** class-sections — it never deletes a subject, teacher, room, class or the session. So the guided setup must not open blank afterwards: `GET /onboarding/session` falls back to answers rebuilt from the school by `answersFromSchool`, flagged `prefilled` and **deliberately not saved** (opening the wizard to look must not create a draft, or `shouldPrompt` offers that school a resume for ever). The client marks every prefilled key touched so the first Next persists them — otherwise a step whose answers lived only in the browser commits nothing and says "There is nothing to create yet". The rebuild carries rooms, curriculum, mappings and class teachers as well as the masters, read for the **active year only** (§3.11).
- **The left nav starts collapsed, every time** (§8.1d). It was built for that state — each item is an icon whose name slides out on hover, so nothing is hidden, only folded — and every screen behind it wants the 172px more than a standing list of labels is worth. Expanding is a deliberate act that lasts the visit; the preference is **not** persisted. Collapsing must set `--sidebar-w` on the document ROOT, never a width on the sidebar, because the §24.5d guided-setup dialog insets itself by that token — set it locally and the dialog keeps a 236px strip of dead page down its left edge. Apply it in `useLayoutEffect`, not `useEffect`: the stylesheet's default is 236px, so a passive effect shows every user an expanded nav snapping shut on every page load.
- **What a teacher teaches is DECLARED, not derived** (§27.13, `teacher_subjects`) — the same correction §18 made for teaching scope, and for the same reason: a fact read back from existing mappings can only describe what somebody has already been given, never constrain what they are given next. It reaches the database through a `Subjects` column on the Teachers sheet. **Absent means "not stated", never "teaches nothing"** — the importer writes it only for rows that named subjects, or an old sheet with a blank column would wipe every teacher's subjects. Readers take the **union of declared and mapped**, because schools predating the table have no declarations. The §23 cascades name it explicitly even though the FK cascades anyway: a silent cascade is a destructive write nobody was shown.
- **A published timetable can be FROZEN, and a freeze is a decision rather than a side effect of publishing** (§29.1, `timetable_config.frozen_at`). Two columns, not a `status` value — `status` already means draft/active/archived, and a timestamp answers *when*. NULL is every school today, so nothing changes until the button is pressed. `FreezeService` is **one definition with four resolvers** (config id · class-section · class+year · any-in-school), the same shape as `assertCanTeach`/`assertSubjectApplies`; §17's Prisma extension was rejected because school scoping reads an ambient context while this needs a lookup per write, and the §14 budget is not the place to pay for that. **Board and draft edits are guarded too** — they touch draft rows, but a draft edited then published is the published week changed by two clicks instead of one, so leaving them out makes the freeze theatre. **Deliberately NOT frozen:** hiring, rooms, subjects, next year's session, cloning, every read/preview/dry-run, and §4.7 availability — "Mrs Rao now leaves at 1pm" is a fact about a person and the one a school records *before* re-staffing; refusing it would leave them unable to write down what prompted the change. The importer and guided setup are the blunt exception (they resolve names inside one transaction, so they refuse while *any* wing is frozen). The call-site shape means a new write path can forget to ask, so **`pnpm test:freeze` is the guard on the guard**: it drives all 28 routes against a frozen timetable, and asserts both that each refuses AND that **each works again after unfreezing** — a guard that refused permanently would pass the first half and have broken the product. The refusal is worded once, in the service; call sites pass only *what* they were about to change. Freeze/unfreeze reuse `timetable.publish` — never add a permission for it.
- **A staffing change is a RECORD, not a mode** (§29.2, `staffing_changes` + `_teachers` + `_items`). A mode switched on and off cannot answer "who taught Class 5-A Maths before September, and why did it move?", which is the whole point. `reason` is an enum because it chooses the default *shape* of the change; **`effective_from` is recorded and never acted on** — a timetable that rewrote itself overnight against a week that has since moved is what §29 was asked not to be. A teacher is `releasing` or `receiving`, **never both** (composite PK): both at once gives two answers to "how full are they?", which is the number every candidate is scored against. **One open change per teacher**, or two plans each look valid alone and collide at apply. `staffing_change_items.unit_id` is polymorphic with **no FK** — §4.7b's argument holds for live rows, but here an FK would erase the record when its mapping is deleted, which is the case you most want the record for; `label` is denormalised for the same reason. **Four things carry "who teaches"** and `staffing-units.ts` must enumerate all of them: mappings, merged groups (one occupancy event however many sections attend, so cells are deduplicated by day/period), **elective options** (`class_section_id = NULL` by design, so anything looking for a teacher's work by section finds none of it), and the class-teacher role (no lessons at all, still has to move). Published rows only, scoped to the config — a teacher in two wings must not be vacated from both. Zero lessons means two different things ("not a lesson" vs "not published yet") and is never left to stand alone. The proof is `pnpm test:staffing`: after opening, reading, editing and discarding a change, the whole published week and all four carriers are **byte-identical** by hash.
- **Reassignment asks a different question from the solver, and deliberately does not reuse `SolverState.check()`** (§29.3, `packages/shared/src/restaff/engine.ts`). `check()` answers "can this lesson go in this cell?"; this asks "can this teacher take this lesson **where it already is**?" — and since the cell never moves (§29.0), forcing the first into the second means building a `SolverVariable` that lies about span, `dayKey`, `samePeriodKey` and the room pools, then discarding most of the answer. It reuses the *data* instead — `buildTeacherCtx`, `effectiveMinByTeacher`, `buildFeasibilitySnapshot` — so it cannot disagree with the solver. Class-side, room-side and subject-side checks are **not** re-run: they are true by construction. Hard filters (each naming itself): §18 guest + scope, §27.13 subjects, §27.16 subject classes, §4.7a availability, alternate-day, occupancy at **every** cell, daily/weekly caps (weekly counts other wings), max-consecutive, `alternate_period`, class-teacher P1. Soft: continuity ≫ specialism > **fractional** spare capacity (a raw count always prefers the part-timer) > §20 shape, which is **scored and never enforced** — completeness outranks shape. Two things a substitute lookup does not need: **the week is mutated as the plan fills it** (three units that each fit alone break a cap together), and the **hardest unit is settled first** (fewest legal candidates, then most periods), then re-sorted into the school's own order. The plan is a **GET** because it is a question. In the API layer the occupancy handed to the engine is the published week **minus the released units, subtracted by slot id — never by teacher**, or a partial release frees lessons still being taught; merged-group rows are deduplicated to one occupancy event per cell (§4.10).
- **The §29.3 ejection pass was justified by search, not by reasoning** (§29.3a). Hardest-first ordering is strong enough that every hand-built case for a depth-1 ejection pass was already handled by it; a random sweep over 4,000 small instances fired it 58 times, and one of those is now a deterministic test. Keep the shape: **depth 1** (chaining makes it a search, and a slow screen is the failure mode), **both halves must succeed** (or a rescue swaps one uncovered class for another and calls it progress), and it may only move units **this plan** assigned — rearranging the school's standing week is §29.0's promise broken from the inside. A 500-instance property sweep with a seeded PRNG guards the three things post-hoc rearrangement breaks: no double-booking, nobody over cap, every uncovered unit explained. `loads[].alert` is §28.1 measured against the teacher's **whole** week including other wings (a line round one wing reads 67% where the truth is 87%) — a warning never a refusal, while over-cap refuses by name. `units=type:id,…` narrows a release so an *adjustment* moves what somebody picks; an unknown key is ignored (the screen may be stale), a selection matching nothing is refused. An uncovered unit shows **every** candidate's reason — the best-only version sent people to fix the wrong thing.
- **Applying a staffing change updates slots IN PLACE and moves the carrier too** (§29.4). The plan is **recomputed server-side**, never taken from the request (§21's rule: a preview is not the list of writes). Slots are updated, never deleted and recreated — `substitution_log` points at slot ids with no FK, so recreating orphans every recorded cover; and since the class and room do not move, only `teacher_occupancy_key` changes. **The carrier moves too** — mapping, merged group, elective option, class-teacher — or the next Generate quietly puts the leaver back with nothing connecting the two events. Every write is **compare-and-set on `teacherId: from`**, so a week that moved since the preview is not overwritten. **A gap is chosen, never discovered**: apply refuses while anything is uncovered unless `acceptGaps` is explicitly true, and an accepted gap **leaves its unit exactly as it is** (nulling the slots would destroy the only surviving statement of what that class needs). **Revert** (§29.5) is built from `staffing_change_items`, never by re-planning, is compare-and-set on what the change did, and **skips and NAMES** anything moved again since; the row is kept and marked `reverted` (§3.14). The proof is `pnpm test:staffing`: after a real apply, every other teacher's week is byte-identical, **no cell moved at all** (row by row, field by field), the same slot ids changed hands, and all four carriers moved while the other wing stayed put.
- **A React context and its provider must not live in one module** (§29.7). `colors.tsx` exported both; Fast Refresh preserves state only for modules exporting components alone, so Vite **invalidated** it on every `hooks.ts` change, minting a new `createContext` object while the grids held the old one — `useContext` then returned the default, which for colours means "no colour", and every cell went white with **nothing anywhere reporting an error**. The context, hook and helpers live in `colors-context.ts` (no JSX, so not a refresh boundary); `colors.tsx` exports only `ColorProvider`. The general rule: **a context whose default means "switched off" fails silently by construction**, so when the default has to stay permissive the module boundary is the only place left to get it right. Watch for Vite's own "Could not Fast Refresh — X export is incompatible" warnings; any file they name that also holds a context has this bug.
- **A subject declares which classes take it, and a declaration is not the ladder** (§27.16, `subject_classes`). §27.15's `from`/`to` ranges guess from the subject's *name*, so they may shape a proposal and never be a rule; this is the school's own answer, so it refuses. Same promotion §18 made from a derived teaching band to a declared one. A row per class, not a range — a range only exists on `CLASS_LADDER` and cannot say "Class 5 and Class 8 but not 6 or 7". **Empty means "not stated", never "no classes"** (invariant 7), which is why the migration has no backfill: backfilling from existing curriculum would recreate the derived fact the table replaces. In `suggestCurriculum` the two filters look alike and are not — the declaration is applied first and never reconsidered, the ladder speaks only for undeclared subjects, and the "stands aside rather than leave a class empty" fallback runs over **what the declaration allows**, or an excluded subject comes straight back through it. Three doors as always: the Subjects master, the guided Subjects step, and a `Classes` column on the Subjects sheet — written only for rows that named classes, exactly as `Teaching Scope` is. `assertSubjectApplies` refuses at the point of the mistake and the Allocation grid refuses the same edit client-side rather than drafting what the commit will reject; **Check 13 is the backstop and is a WARNING**, because unlike Check 8 nothing wrong is *enacted* — two statements merely disagree, and blocking a whole school over that turns a convenience into a trap. No remedy: one way out deletes teaching the school may really do, the other widens an answer somebody gave on purpose. `ChipPicker` **summarises above three** ("11 of 14 classes", names in the `title`) — "All N" alone broke the moment one class was removed and thirteen chips came back.
- **A published timetable can be withdrawn, and withdrawal FLIPS rows rather than copying them** (§3.14). `substitution_log` points at slots by id with no FK, so copy-and-delete would orphan every recorded cover and a republish would mint ids none of them match; flipping keeps every id, which is what makes publish→withdraw→publish a genuine round trip. It goes back into the draft it was published from **only when that draft is still empty** — `draft_scope` is in all three unique keys, so flipping a week into a draft that already holds one collides on the first cell — otherwise into a new one. The publication row is **kept and marked withdrawn**, never deleted: deleting it would renumber the next publish back to v3 and rewrite the school's record of what was on the wall. Needs `timetable.publish` (not `timetable.edit`, which only ever *adds* a working copy), leaves §18 extras and archived drafts alone, and notifies the teachers who were told it went live.
- **A subject belongs to a rung of the ladder, and a class may be taken off it** (§27.15). Each `WEIGHTS` family carries an optional `from`/`to` on `CLASS_LADDER`, so Biology is not proposed to Pre-Nursery — but it **shapes the proposal, never a rule**: an unrecognised name is offered everywhere, and a range that would leave a class with *nothing* stands aside, because the school's own subject list is better evidence than the ladder. Saying "this class does not take this subject" is a real deletion (`allocation-cell.ts`), not zero periods — zero leaves the teacher mapped to a subject nobody is taught. It is the one place the draft-only wizard writes to the server, and it has to be: the §16 importer skips by natural key and removes nothing, so a committed curriculum row would survive while the cell looked empty, and **an empty cell that does not mean "not taught" is worse than no delete button, because it is believed**. Refuses **narrowly** — only if the published timetable teaches *that* subject to *that* class — and asking twice is `{ok:true, total:0}`, never a 404. Relatedly, the Allocation grid's fallback to the proposal is **per wing**: a class emptied on purpose must stay empty, but a wing the plan has never covered must not open blank.
- **`.sidebar` needs its own `z-index`** (§8.1d). `position: sticky` creates a stacking context *unconditionally*, so the collapsed nav's hover flyout — `position: fixed`, `z-index: 60` — was only competing inside the rail; the rail itself painted at `auto` and the page content covered the label as it slid out. The rail sits at **50**: above the sticky topbar (5), below the §24.5d pane overlay (200), which is meant to dim the nav rather than duck under it. Nav items carry `aria-label` but **not** `title` — with the flyout painting correctly the two arrive together and say the same word twice.
- **The masters edit BESIDE the list, never below it** (§8.5, `masters/MasterPane.tsx`). §8.1c had already written the reason down for the Curriculum step — *"a form below the table means pressing Edit scrolls the row off the screen"* — and it applies to every master: Edit scrolled the form into view and the row out of it. Two columns, each scrolling inside itself, and **the page never scrolls**; the list keeps the remaining width and the form is a fixed 340px, because a form's width is set by its widest control while a six-column table always uses more. **One component, not four** — the same arrangement copied four times is why this had to be fixed four times. The form's heading is the state indicator ("Editing Class 5-A" vs "Add a class-section"), since the only previous answer was a button label below the fold. **Classes** puts class-sections in the list (they are the §3.10 scheduling unit, and where "belongs to no timetable" is visible) with classes in the form column; §25's term calendar and the read-only Lessons view moved out of the stack for the same reason. Teachers is untouched — it already swaps the whole pane. Two traps: `DataTable` wraps its table in an `overflow-x: auto` div, which is what a sticky header would stick to (a box with no height that never scrolls vertically), so the pane takes the scrolling instead; and anything stacked *below* the panes brings the page scrollbar straight back.
- **Patterns:** master-data screens are **list-first, form-second** (directory table with Edit per row; Add/Edit opens the form) — *except the manual Curriculum step (§8.1c), which edits **in the row***, because at 14 classes × 8 subjects a form below the table means pressing Edit scrolls the row off the screen. Long master tables get filters before they get a better form: the fastest edit is the one where nobody scrolled to find the row. Class-Teacher Assignment (writing `class_sections.class_teacher_id`) is a distinct screen from Subject Mapping. Merged-group cells show a link icon and drag as one unit.

## Build phases (roadmap, §12)

1. Masters + Config + **Feasibility Engine** (live Readiness Score before any solver code)

## Conventions for working in this repo

- Treat `AI-Timetable-System-Architecture.md` as the spec; if implementation needs to deviate, update the doc in the same change and call the deviation out.
- Solver code must stay CPU-isolated from the API (BullMQ background job with WebSocket progress) — never run generation inline in a request handler.
- Reuse the *same* constraint-check functions for solver placement, drag-drop legality, and the "suggest legal destinations" mode — one rules engine, three call sites.
- Section references like "§4.7" in commits/discussions refer to the architecture doc's numbering.
